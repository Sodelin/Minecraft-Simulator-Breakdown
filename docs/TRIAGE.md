# Review triage and research directions

This is a focused review of the purchased MCMacro source and supplied replay fixtures. It is not an exhaustive audit of Minecraft, every source path, or the video. Findings below distinguish implementation defects from assumptions and research choices. File and line references point to the **unmodified purchased files**; patched files may have different line numbers. Detailed implementation and test results belong to the accompanying audit report.

Priority here measures practical consequences for building, reproducing and interpreting results. It does not measure the creator's competence or the importance of the whole project. A repair should not consume additional random numbers merely to improve logging; paired fixed-seed checks should demonstrate that observational repairs preserve the modeled trajectory.

## Review next: assumptions that need calibration

The project README explicitly describes an abstract, event-driven model conditioned on a rare self-beatable seed. The Source Architects README explicitly calls End clutter, erosion and route explosions constrained reconstructions rather than tick-perfect histories. Those are disclosed choices, not discoveries of dishonesty.

| Topic | Why it matters | Useful next experiment |
| --- | --- | --- |
| Meaning of “no player” | Zero players ever present, no player inputs after setup, and continuously loaded chunks are different experiments. Dragon initialization, natural spawning and chunk activity can change feasibility. | Freeze the exact initial state, Minecraft version, loaded regions and permitted external support; test each necessary mechanism in that environment. |
| Competing clocks and coupling | In the hybrid chain, some processes are selected through per-loop choices while others add elapsed time. A loop iteration is not automatically equivalent to a shared continuous-time process. | Write the intended generator/event hazards; compare a small exact competing-event simulation against the compressed scheduler. |
| Macro movement | Exponential macro-node crossing times summarize many local random strolls. First-passage times, survival, terrain and return probabilities can depend on entry location and past movement. | Fit and validate transition distributions against vanilla traces, including withheld geometries and boundary cases. |
| Placement and encounter rates | Fixed placement/encounter probabilities and large waiting-time constants can dominate the final duration. Mathematical consistency alone cannot establish their vanilla values. | Publish units and provenance per rate; run sensitivity analysis and calibrated local fixtures. |
| Structure inventories and spatial scale | Exact structure placement does not automatically establish exact generated loot-room inventories or representable far-world volume. | Check actual generated blocks and biome eligibility on fixed seeds; validate area/volume accounting against the chosen world geometry. |
| Dragon damage and crystal routes | A constrained reconstruction can establish a mechanism within its model without showing that a continuous vanilla history reaches every depicted state. | Validate each necessary transfer, block placement, projectile and explosion geometry in the matching game version, then check dependencies between fixtures. |
| Assisted versus unassisted runs | Probability changes such as RNG assistance alter the sampled model unless properly accounted for. | Label assisted demonstrations separately. Use unmodified rates for probability estimates, or use a formally weighted rare-event method with validated weights. |
| Units and reporting | A “year” is a model unit. It must not silently become an Earth year or a runtime estimate. | State ticks per model year and the assumed tick rate; print both model time and any explicitly defined wall-clock equivalent. |

## Define the objective before searching for an optimum

Several useful objectives conflict. There is no single established “optimal simulator” here.

| Objective | Quantity to optimize or estimate | What counts as evidence | Main trap |
| --- | --- | --- | --- |
| Mechanism feasibility | Whether a permitted sequence exists | Matching-version vanilla fixtures plus a dependency-consistent initial state | Treating a model-generated story as a vanilla existence proof |
| Conditional completion probability | Probability of death by time T, given a specified seed/setup | Registered ensembles with all runs, explicit assumptions and uncertainty | Reporting only winners or ignoring censored runs |
| Completion-time distribution | Quantiles and survival curve under a fixed experiment | Unassisted trajectories, censoring-aware analysis and calibrated clocks | Calling the fastest observed run a typical waiting time |
| Fast conditional witness | Minimize modeled completion time over a declared seed/configuration space | A reproducible witness with search budget and constraints | Conflating favorable-seed search with an unconditional Minecraft probability |
| Computational efficiency | Minimize compute cost at a fixed error target | Benchmarks against a validated reference | Making the model faster by dropping decisive failure mechanisms |
| Scientific accuracy | Reduce predictive error and uncertain assumptions | Out-of-sample vanilla comparisons and sensitivity results | Increasing model detail without validation |
| Visual explanation | Maximize understandable, truthful causal explanation | Replay provenance, faithful timestamps and clear abstraction labels | Presenting interpolated visuals as recorded block histories |

A sensible order is: repair the observability defects; specify the experiment; validate indispensable local mechanisms; calibrate the coarse model; then choose a probability-estimation or constrained-search objective. Absorbing Markov or semi-Markov models may help small dependency networks. Gillespie-style scheduling may help known competing hazards. Rare-event splitting or importance sampling may help probabilities too small for direct Monte Carlo. None is automatically superior: their assumptions, state reduction, bias and uncertainty must be tested against the intended experiment.

## Provenance and historical reproduction

The supplied manifests identify Minecraft 1.21.4, while the source integration README describes obtaining a matching MCP-Reborn 1.21 workspace. That broad label does not establish that every mechanism or historical result was validated on the exact target version. Record the integration build, mappings, game version, native source hash and manifest hash explicitly. Older-version code witnesses can help identify questions; they cannot certify 1.21.4 behavior.

The historical updated replay has not been reproduced from the available source and default settings in the review's 45-second attempt. A wall-time-limited attempt is not a proof that the historical result is impossible. The devlog describes an evolved replay and same-world batches that retain the most successful run, but a targeted search did not locate the exact command or its event RNG seed. Its precise source revision and full configuration therefore remain unresolved. **Do not infer that the shipped replay used RNG assistance from this reproduction gap.** Preserve this as an explicit provenance question for the author.
